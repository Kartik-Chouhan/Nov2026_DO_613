****DOCKER****

When we say docker in AWS, it means we're referring to docker containers. Docker is a service which will containerize the application. AWS provides
docker to auto scale, manage, and run those containers. For any application, Docker can package your application, and AWS can run it without 
requiring you to manage every part of the infrastructure yourself. Docker contains everything needs to run an application like code, libraries, 
dependencies and system tools.

Some main terms and services that are used with Docker:

1. AWS ECR: (Elastic Container Registry) - It is a managed registry for storing Docker container images.

2. AWS ECS: (Elastic Container Service) - It will manage the containers in AWS. We can just "fargate" to run the containers without managing the servers.

3. Docker Image: Docker image is a read only package containing everything which is required to run an application. Like app code, dependencies and 
				 other configuration. Think of a docker image as a template from which you create and run docker containers.

4. Docker File: A docker file is a script that contains a series of instructions on how to build a docker image. Instructions like how to create image,
				which base image to use, how to install dependencies, what commands to run when the container starts. Some imp base files are:
				
				i) Alpine
				ii) Ubuntu
				iii) 369

5. Docker Engine: A docker engine is the core component of docker service which allows you to create, start, stop, manage the docker containers and
				  images.

6. Docker Daemon: It is the background service that manages containers, images, networks, and storage volumns.
				  "Docker-d" is one of the popular docker daemon. but, now a days "Container-d" is getting used.
				  
7. Docker Compose: It is a tool for defining and running multi-container docker applications, with a simple YAML file. Here, It can configure
				   multi-service containers like container for web app and db etc. We can interact to docker daemon through docker CLI.
				 
8. Docker Registry: A docker registry is the place where docker images are stored, managed, and can be downloaded. "Docker Hub" is the most popular
					public registry. We can say like it is a git repo for the docker images. Nexus, Jfrog are the e.g of docker registry.
					
9. Docker Networking: It allows the containers to communicate with each other. Also, to the external networks.
					--> imagine your Java Spring Boot application runs in one container and MySQL runs in another. Docker networking allows 
						 your Spring Boot container to connect to the MySQL container.
					--> Some imp docker network types:
						--> Bridge Network: It is default network for standalone containers. In this, Containers are isolated from external 
											networks unless connectivity is configured.
						--> Host Network: In this, the container shares the host's network namespace.
						--> Overlay Network: Allows services on different hosts to communicate over a shared virtual network.
						--> None Network: Disables normal container networking. Useful when a container does not need network connectivity.
						
10. Volumes: Volumes are used for persistent storage in docker containers. By default, the docker containers are ephemeral means it will lost the data
			 once the volume is destroyed or removed.

11. To run the docker file. We've to install the terraform and aws using winget cmd.

****KUBERNETES(K8s)****

It is an open source container orchestration platform that automates deploying, scaling, networking, and managing containerized applications.

For example, suppose you have a Spring Boot application packaged as a Docker container. Kubernetes can run multiple copies(replicas), restart failed 
containers and scale the application when traffic increases. K8s handles the tasks such as:

--> It helps manage apps across cluster of machines, ensuring HA and scalability and reliability.
--> Deploying and managing containers.
--> Load balance traffic.
--> Managing n/w and storage.

--> CNI: Container Network Interface - It is the n/w interface to provide connection or communication b/w the nods. e.g) Calico, Cillium etc.
									   Calico, Cilium are the tools which can replace kube-proxy.

--> CCM(Cloud Controller Manager): This will allow the communication b/w K8s and other AWS resources. Also, it manages the cloud-specific components,
								   such as load balancers and storage volumes.
--> Usually, the number of containers and nods during the setup of K8s will be decided by Architect.

--> Namespace: It is used to logically separate and organize resources within the same K8s cluster. A channel of communication can be build to provide
			   communication b/w the namespaces. If no any name is given then it will take the default namespace.
			   A namespace is like the different rooms in a building. Where, each room can an contain its own applications, Pods, Services, and Deployments.
			   In K8s, namespace can't be renamed once done the configuration. If we want to rename, we've to create another namespace and migrate the services.		
			   Cmd to create a namespace: kubectl create ns namespace_name.
			   Every application will create it's own Namespace. If we want to deploy the app using kubectl then first we've to create the namespace.
			   
--> Services: A service in K8s is a logical group of pods and provides a stable way to access them. Since the pods are temporary and their IP add.. can
			  change, a service can provide a stable IP add., a DNS name. Types of services:
				1. NodePort: In this we can define the port in range(30000 - 32767). In this the public IP of K8s will be exposed.
				2. ClusterIP: It is the default one which is used to provide communication b/w microservices.
				3. LoadBalancer: It Uses an external load balancer. It will automatically define the IP address.
				4. External Name: If the traffic is getting served b/w service to service.

**Components of K8s**

1. Master Node: It manages the cluster and we can say like it is a control plane K8s. Here, the number of master node will be in odd no's always
				because it will take the decision to manage the container. The brain of Kubernetes which makes decision on which cluster the app will run.

2. Worker Node: These are the nodes on which EC2 instance will run. It will run your app.

**Components of K8s(Master Node)**

1. Kube-api: It is like a API gateway which provides the communication b/w Master & Worker node and there components. Also, 
			 The main entry point for Kubernetes commands and API requests. All the components will communicate with Kube API server.

2. etcd: It stores Kubernetes cluster configuration and state, including information about resources and desired workloads. It is a metadata of pods.
		 It also stores data about the pods. If we want to get and access the backup of K8s, we can take it from etcd.

3. Controller Manager: Runs controllers that continually work to make the actual cluster state match the desired state. 
					   For example, it helps ensure a Deployment has the requested number of replicas.
					 
4. Scheduler: Selects a suitable worker node for a newly created Pod based on resources and scheduling rules.
			  The scheduler will watch for the newly created pods that have no assigned nodes and will select the appropriate worker node for them.

**Components of K8s(Worker Node)**

1. Kubelet: It is an agent that runs on each worker node. Ensures the Pods assigned to the node are running as specified.
2. Container runtime: Runs containers, commonly using "containerd" & "CRI-O" or another supported runtime.
3. Kube-proxy: Helps provide service networking, depending on the cluster's networking setup. It is to manage the n/w of nodes.
4. Pods: The smallest deployment unit that run your application and holds containers. A pod can contain multiple services or containers. A pod will be 
		 having an IP. If we want to see the IP of each pod created annd running in our K8s, we can use below cmd. Pod will be created by controller manager.
		 
		--- kubectl -A -o wide 
		 
5. Container Run Interface: It will create the container by taking the image outside or from docker hub. In Simple, it is used to pull the docker image.

Developer builds and pushes a Docker image, deploys it using kubectl, the control plane schedules the Pod on a worker node, kubelet starts the 
container, CNI configures networking, and Service/Ingress exposes the application to users.

Remember these 6 words:
Code → Image → Registry → Deploy → Run → Access

****HELM CHART****(IMP)

Helm is a package manager for K8s. While, the Helm Chart is a package container containing yaml files, configuration files which are needed to deploy
an application into a K8s cluster.

For e.g) Suppose, we're having three cluster or nodes in which we want to deploy the application which is following the same deployment configurations,
now we've to write configuration file for each and every node or cluster. But, using the Helm Chart we can use the same file for all three nodes.

Like this we can increase the re-usability by packaging the configuration files. So, we don't need to maintain in every cluster or node.

To remember, as we have npm for node.js, maven or gradle for java, similarly we've helm for K8s.

***Key Components of Helm***

1. Helm Chart: It is a pre-defined package or collection of files including required dependencies and configurations.
2. Helm Client: It is the cmd-line tool using which we can manage charts and release applications.
3. Helm Repository: It is a location where helm charts are stored and shared, similar to a software or git repo.
4. Helm Release: It is a specific instance of a Helm chart deployed to a K8s cluster when we install a chart, it creates a release.					  

**Flow of Helm: How helm works?

1. Create the Chart: At first, we'll create the helm chart containing the several configuration files like deployment, services, ConfigMaps ect with 
"Chart.yaml" as the primary metadata file.

2. Install the chart: Here, it will fetch all the vlaues and config present in "Chart.yaml" and will install and send the chart to the K8s cluster.

3. Upgrading and managing Releases: Helms allows we to upgrade the application to the latest version from the official helm website. We can also use
the below cmds to install it on various systems:

For linux: curl "download link from helm official website"
For windows: download directly from the releases from official website.
To check helm version: helm version
To check on which cluster you're working: kubectx
To switch the cluster: kubectx cluster_name
To list out the repo in helm: helm repo list

--> Bitnami: It provides packaged applications and deployment solutions that make it easier to install and run software. In the Kubernetes world, 
Bitnami is especially known for ready-to-use Helm charts and container images for applications such as PostgreSQL, Redis, NGINX, and WordPress.

--> CRD: "Custom Resource Defintion": This we can use to customize any resource definition as per own requirement and labelling.
		In simple, CRD will teach the K8s about the new resource type.
		
--> _helpers.tpl:- It is a resuable function library for helm templates.

****AWS ArgoCd****

ArgoCD is a GitOps based continuous delivery tool in AWS which we can use to deploy and manage the apps in K8s. In AWS, ArgoCD is commonly 
installed in EKS cluster.
						ArgoCD will monitor the Git repo continuously and it will sync the changes b/w git repo and the cluster state. 
As soon as the change will happen in git repo, it will sync the EKS cluster state to that change automatically.  

Q) We call ArgoCD as GitOps?? -- Because here, the git will act as a "source of truth". Below are the some imp cmds used in ArgoCD:

1. kubectl get pods -n argocd ---> This cmd will check and list the ArgoCD pods.
2. argocd app list ---> This cmd will list out the argocd apps.
3. argocd app get app_name ---> This cmd will tell the status of argocd application.
4. argocd app sync app_name ---> This cmd will sync the EKS cluster with git repo changes.
5. argocd app rollback app_name 1 ---> This cmd will rollback the CD to previous version.
